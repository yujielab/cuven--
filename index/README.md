# Cuven ᴿ 索引库 Worker（v6.4）

论坛（电影 fid=44 / 剧集 fid=2）→ TMDB 认定 → R2 索引；对照片库总账（Stream 写的 `Received.json`）标出「库中已有」，
目录默认只显示缺片；片单里的种子由浏览器攒齐、本地打成一个 zip。代码：[`worker.js`](worker.js)。

## v6 改了什么

### 一、缺片检测重做

v5.4 判「我有没有这部」用三条太宽的规则：

| v5.4 | 后果 | v6 |
| --- | --- | --- |
| 认下来（有 TMDB id）的条目也照样按「片名 + 年份 ±1」建模糊键 | 库里有「惊变 2023」，另一部「惊变 2024」被当成已有藏掉 | 可信 id 只按 id 比 |
| 没年份的条目只按片名撞 | 一个 `Dune.mkv` 把 1984、2021 两部《沙丘》都藏掉 | 一个条目只「认领」一部；同名多部取年份最贴近的，并列就谁都不认（显示出来，不悄悄藏掉） |
| Stream 认错的 id 照单全收 | 认错的那部被判「确定已有」，真正那部显示缺片 | id 的年份与文件名差一年以上（剧集：早于首播一年以上），或中英文名与文件名全对不上，判为认错，按文件名比 |
| 片名只做小写去符号 | 繁体、全角、重音、罗马数字、冠词、「第二部 / Part Two」全对不上 | `canon`：繁转简（与 Stream 字幕繁转简同一张表）、全角半角、去重音、II→2、去冠词、第二部→2 |
| 剧集按电影的年份规则比 | 「黑镜 第三季 2016」对不上首播 2011 的《黑镜》 | 季目录年份允许晚于首播 |

另外两条：
- **名字互相矛盾不认**：只有英文名「City」「Home」撞上、中文名完全不同的，多半是两部片。
  例外是港台译名：英文名够长（≥ 8 个字母）且同年时照认，所以「星際效應」仍能对上 Interstellar。
- **两边 id 不同的推断**：片名、年份全同，而且索引里根本没有库里那个 id，就判为「很可能已有」。
  这多半是某一边认错了 id。

判定分三档：`2` 确定已有（id 相同），`1` 很可能已有（界面上的「疑似已有」），`0` 缺片。

**准确率**（`tests/match-synth.mjs` 的随机样本：六千部片海，含重拍、同名、续集；片库条目按比例加了繁体、全角、
去冠词、罗马数字互换、缺年份、年份差一、Stream 认错 id 这些噪声）：

| | 误藏（缺片被藏） | 漏判（有的显示缺片） | 精确率 | 召回率 |
| --- | --- | --- | --- | --- |
| v5.4 电影 seed 1 / 2 | 700 / 707 | 67 / 47 | 66.5% / 65.8% | 95.4% / 96.7% |
| **v6 电影 seed 1 / 2** | **12 / 4** | **6 / 3** | **99.2% / 99.7%** | **99.6% / 99.8%** |
| v5.4 剧集 | 308 | 84 | 68.0% | 88.6% |
| **v6 剧集** | **5** | **6** | **99.3%** | **99.2%** |

剩下的错误都是信息不够、本来就判不准的情形：
- 没年份的文件名碰上重拍片；
- 两部片英文名相同、年份相同、中文名不同；
- 片名太短又没年份的条目，刻意不认。

手写的标准答案（`tests/match-cases.mjs`，39 条线上常见形态）全部判对；同一份答案 v5.4 是电影 20/31（误藏 3、漏判 8）、剧集 5/8。

**速度**（2.9 万部片的索引 × 1.5 万条片库）：
- 判定整张表按「索引版本 × 片库成品」算一次。查目录时每部片只剩一次数组读取，不再做字符串归一化：每次查询 **35ms → 8ms**。
- 冷启动后第一次查询要建表（约 0.1–0.3 秒）。比对键在建索引时就算好，存在影片记录的第 17 位；片库成品里也存了一份。

### 二、存储：原子提交与多重兜底

| 问题（v5.4） | v6 |
| --- | --- |
| R2 读到一半断了、JSON 解析失败都被当成「对象不存在」，下一次写会用空表覆盖整个索引 | 不存在才给默认值；读失败重试后报错，这一轮不写任何东西；内容损坏拒绝覆盖 |
| 分片、tid 表原地覆盖，平台掐在中间会留下对不上的几份；帖子可能被 tid 表挡在门外，永远进不了索引 | 分片与 tid 表 copy-on-write（键里带代号），写 `state.json` 才算提交；被替换的旧对象十分钟后才删，删前再核对没被引用 |
| 锁只是一个时间戳，两个 isolate 能同时抢到；锁过期被接管时原任务照样提交 | 锁带身份，用 R2 条件写抢锁；提交前、写留底队列前都核对锁并续期，锁被接管就放弃这一轮 |
| 没有「影片表只增不减」的检查 | 建索引、增量、重试这些操作里影片表变少就拒绝提交；重置 / 清理孤儿骤减一半也拒绝 |
| 无备份 | 定时任务每天备份 movies / state / 留底队列（`bak/<源>/<日期>/`，留 7 天）；体检里「从备份恢复」「立即备份」 |
| 掐在 movies.json 与 state.json 之间：计数漂移 | 两者带同一个提交号，对不上就记 `heal`，定时任务自动「重算汇总」 |
| — | 被掐掉的轮次留下的、没人引用的新代号对象，每日维护清掉（放了六小时以上的） |

### 三、其它兜底

- **源闸门卡死**：后台任务永远不结束时，闸门会一直对另一个源回 409。现在两分钟没有任何进出就强制放行。
- **出站请求超时**：所有出站请求默认 20 秒超时（TMDB 12 秒，海报 15 秒）。
- **海报代理**：上游断网时回 502，不再抛异常。
- **种子按 bencode 逐层解析**：v5.4 找第一个 `4:info`，文件名或注释里有这几个字就会算错 btih；种子被截断还会死循环，直到超出 CPU 被掐。
  现在下载回来先校验，不完整的直接报出来。
- **取件**：遇到限速、断网、论坛 5xx，标成「稍后重取」，浏览器每部最多重试 4 次，并且退避。
  「没有附件」「需要积分」这类不会自己好的直接报失败。
- **目录参数**：页码、评分参数乱填时按默认处理。

### 五、极限模式（v6.2，默认开）

普通模式一轮的天花板是「一次调用 50 个子请求」：3 页列表 + 最多 20 组 TMDB 认定。
一页二三十个帖子，一轮认不完，就只好把游标往回拨，下一轮重抓同几页。

极限模式把一轮拆成三个角色，各用各的那份配额：

| 角色 | 做什么 | 配额 |
| --- | --- | --- |
| 扫描轮 `/api/build?turbo=1`（持锁） | 只抓列表：一轮 12 页，同时 4 条。认识的片直接挂上；不认识的连同帖子行进留底队列（标 `wait`），游标一口气推到底。顺手把浏览器交回来的认定结果写进分片 | 一次调用的 50 个几乎全给列表页 |
| 认定工 `/api/tm`（不持锁、不写 R2） | 只做 TMDB 认定，结果交回浏览器 | 每路一次独立调用，自带一整份 50 个；浏览器同时开 3–6 路 |
| 浏览器（页面里的 `turboRun`） | 排队、并发、退避、背压；把结果攒着交给下一轮扫描 | — |

**不会丢、不会重复**
- 帖子行任何时候都只在两处之一：已提交的分片，或留底队列。掐在哪一步都不丢（测试里交回结果的那一轮每一次写之后都掐一次）。
- 已写进分片的留底条目不当场删，记进 `state.pdone` 跟着提交走，下一次写留底队列时才真正删掉。
- 同一批结果交两遍不会重写；浏览器交回来的结果逐字段核对，形状不对的拒收、条目原样留着下次重认。

**放慢与兜底**
- 论坛请求的起点由限速治理器错开：下限 120ms（普通模式 240ms），被限速照旧翻倍、连挨四次就冷却。
- 冷却期只挡论坛：这一轮不抓列表，认定结果照样写进去。
- 认定工的并发是 AIMD：连着两批顺利就 +1；挨了 429、或一批里三成以上没回来，就减半并歇 2.5 秒。
- 排队太长（Free 计划 360 组），先停抓，扫描轮用闲着的子请求自己认。
- 认定工用不了（回 403 或一直报错），也由扫描轮自己认。
- 留底队列快满，退回当场认。
- 停止时不再派新活：等手上的认定工回来，把攒着的结果交上去再停。没交上去的也不丢，条目一直在留底队列里。
- 中途关掉页面，排队的条目由普通模式的「继续建立索引」或每天的定时任务接着认完。
- 总开关：`TURBO=0`。一个变量退回普通模式，页面上的开关会灰掉。

**测得**（`tests/turbo-bench.mjs`：同一个论坛、同样的延迟，并模拟每次调用 6 条并发连接）：

| 场景（2 年 × 150 部、746 个片源，每页 30 帖） | 普通模式 | 极限模式 | 倍数 |
| --- | --- | --- | --- |
| 论坛每页 450ms · TMDB 160ms · R2 25ms | 39.0 秒（17 轮） | 12.8 秒（9 轮扫描 + 17 次认定工） | 3.0× |
| 同上，普通模式换成合并前的 v6.1 | 42.8 秒，**只建出 244 部 / 594 个片源** | 12.8 秒，300 部 / 746 个片源 | 3.3× |
| 论坛每页 900ms · TMDB 250ms · R2 25ms | 60.8 秒 | 18.9 秒 | 3.2× |

延迟带 ±30% 抖动，每组只跑一次，倍数有几个百分点的出入。极限模式的瓶颈是列表页：一轮 12 页约 2.8 秒，认定工基本跟得上扫描。

v6.1 那一行少了 56 部，不是测速误差，是一直存在的丢片 bug（见下面「顺手修掉的」第二条）。
**升级到 v6.2 之后，在「未匹配片名」里点一次「重扫未匹配」**：游标倒回第 1 页，已入库的帖子按 tid 表跳过，只补漏掉的。
测试里用 v6.1 原版建一遍、升级后重扫，片数补齐。

**顺手修掉的（普通模式同样受益）**
- 第二轮（换原名）搜索断网，被判成「认不出」，帖子行只留 12 条。现在按网络失败处理，下轮再认。
- **普通模式会丢片**：一轮认不完的组，只把游标往回拨 ceil(n/28) 页。一页不到 28 组时，前面那几页里没认完的组就再也抓不回来；网络失败的那组只要不在最后几页，也一样。现在没认完的连同帖子行进队列，下一轮先认。
- 同名同原名的两部片（重拍）共用一个键。留底条目会把两年的帖子并在一起，重试时全写进一年，另一年的增量扫描再挂一遍，就重复了。现在每行带上自己的年份。
- 锁每轮只核对、锁龄超过 8 秒才续写，每轮少写一次 `state.json`（R2 同对象写入限流少撞）。
- 冷启动时并发抓页只登录一次。

### 六、缺片检测以 Stream v25 的实时清单为准（v6.3）

**问题**：库里有的片还显示成缺片。
片库对照读的是总账 `Received.json`，它是 Stream **v22** 写的；v25 不再写它（v25 的前端也写着「后端没有总账」）。
所以这边一直拿一份停在 v22 的快照比，之后进库的片全被判成缺片。

**现在**以 v25 自己维护的实时清单为准。清单和旧总账在同一个 R2 桶里：

| 对象 | 内容 | 用法 |
| --- | --- | --- |
| `lib-ptr.json` | 库快照指纹（几十字节） | 指纹没变就不下正文 |
| `file-list-v2.json` | 电影目录下的全部视频文件（Dropbox 增量同步） | 哪些电影在库里，以它为准 |
| `tv/list-v1.json` | 剧集表，每部带 v25 认好的 `tmdbId` | 哪些剧在库里、各是哪个 id |

电影的 TMDB id 按这个顺序来：
1. 总账里同一个文件的可信 id（总账只当提示表；它不会再变，只下载一次）；
2. 这边按文件名用 TMDB 认定。只有英文名的外语片（`Parasite.2019…`）中文结果对不上，就用英文再搜一次；
   认出来的年份和文件名差一年以上，不认（同名的重拍、老片）；
3. 认出来之前：文件名和论坛发布名切出同一个片名键、而且同年的，直接判为已有（一个 TMDB 请求都不花）；
   其余按片名 + 年份认领，标「疑似已有」。

**拿不到清单时**
- R2 桶没挂在 `RECV_BASE` 那个公开域名上：配 `STREAM_BASE` + `STREAM_KEY`（= Stream 的 `AUTH_SECRET`），
  走 Stream 的 `/api/all`、`/api/tv`（`POST /auth` 换会话 cookie，缓存 6 小时）。
- 两条都拿不到，才退回总账。片库面板和体检都会写明「总账停在哪天，之后进库的片会显示成缺片」。

**兜底**
- 清单突然少了一大半（Dropbox 列到一半出错），不用它，判定照旧。
- 文件名只在第一次见到时切一次（一个约 15µs），一次同步最多新切 800 个，剩下的下次接着切。
- 片库面板显示：文件数、带 TMDB id 的部数（总账 / 这边认定各多少）、待认定数，有「认定」按钮。
  每天的定时任务也会接着认。

### 七、未匹配处理管线升级、剧集乱码修复（v6.4）

**剧集片名全是乱码**：剧集版块的页面是 UTF-8，旧版一律按 GBK 解码。
「余生有你」存成了「浣欑敓鏈夊姩」，片名切不出来、TMDB 认不出，五千多组全进了「未匹配」。
认上的那些也只靠英文那一截，可能认错。
- 解码改成按页面真实编码：
  - 响应头或 `<meta>` 声明了 UTF-8，就按 UTF-8；
  - 没声明的，能按 UTF-8 严格解开就按 UTF-8，其余按 GBK。GBK 的汉字几乎不可能凑成合法的 UTF-8，所以这样判断很稳。
- 已经存进去的乱码能认出来：把它按 GBK 编回字节、再按 UTF-8 解，能还原成像样的中文就是乱码。
  「未匹配」面板和体检会提示，并给「重建剧集索引」：
  - 先自动备份；
  - 再清空这个源的索引（另一个源不动）；
  - 最后用极限模式重新抓。
  乱码已经写进分片，tid 表又会挡住重抓，只能整源重来。

**电影认不出的那几百组**：多是外语片。TMDB 上没有中文译名，中文结果里的标题是意大利语 / 西班牙语原名，论坛给的英文名对不上。
还有「没人知道我在这/歌手的秘密」这种一个标题里带两个译名的。
认定从两轮改成最多五轮，每轮只给还没认下的组再搜一次：

| 轮 | 搜什么 |
| --- | --- |
| ① | 洗过的中文名 + 年份 |
| ② | 原名 / 中文名原样 / 不锁年份 |
| ③ | 英文名 + 年份，用英文搜（拿英文片名比） |
| ④ | 别名：「A/B」拆开、「主标题：副标题」只留主标题 |
| ⑤ | 英文名去掉副标题 |

- ③–⑤ 认出来的要求年份对得上（差一年以内）。
- 英文那几轮认下来的，片名用论坛给的中文名。
- 配额不够、或者中途断过网的，不下「认不出」的结论，下次再认。
- 规则版本升到 v3：以前「认不出」的结论全部作废、重试次数归零。

**「重试匹配」更快**：极限模式开着时，可重试的条目整批排进队列，交给浏览器的认定工并行认。
以前一次调用认 10 组，五千组要几百次调用。认不出的记一次重试，满 3 次进「反复认不出」。

## 部署

- **变量**：必填项不变（`SITE_USER` / `SITE_PASS` / `TMDB_KEY`，R2、KV 绑定，`RECV_BASE` 或 `STREAM_BASE`）。
  可选的 `TMDB_BASE`：TMDB 走自己的反代时填。
  可选的 `TURBO`：填 `0` 关掉极限模式（默认开，不用配）。
  可选的 `STREAM_KEY`：Stream 的 `AUTH_SECRET`。只有 Stream 的 R2 桶没挂在 `RECV_BASE` 那个公开域名上时才需要（见上面第六节）。
- **升级到 v6.4 后**：剧集「未匹配」面板如果提示「片名是乱码」，点「重建剧集索引」（会先备份，重建完自动开始重抓）。
  电影那边点一次「重试匹配」，用新的认定规则把以前认不出的再认一遍。
- **升级到 v6.3 后**：在系统页「片库对照」里点一次「重新同步片库」，看面板上写的来源是不是「实时清单」。
  如果还写着「总账停在 …」，按面板上的提示配 `RECV_BASE` 或 `STREAM_KEY`。
- **极限模式默认开**：系统页「继续建立索引」上方有开关，状态记在这台设备上。跑任务时开关锁住，一次任务只用一种模式。
- **首次运行**：直接覆盖部署即可，v6 能读 v5.4 的索引并接着建（测试里覆盖了这一步）。第一轮建索引会顺手给老影片记录补上比对键；
  第一次同步总账会把 `A/list*.json` 升到 v7。
- **R2 里多出来的东西**：
  - 带 `.g<代号>` 的分片、tid 表；
  - `bak/movie/`、`bak/tv/` 下的每日备份。

  老的无代号分片在第一次被替换后十分钟删掉。
- **不能直接回退到 v5.4**：v5.4 只认无代号的老键名，v6 写过之后这些键会被替换并清掉。
  要回退，得先把整个 R2 桶的 `idx/` 前缀备份出来。

## 没有验证到的

- **准确率是在随机生成的样本上量的**，不是你的真实片库。真实数据的分布不同：英文名撞车没有样本里那么多，港台译名可能更多。
  上线后看片库面板里的判定明细（id 相同 / 片名认领 / 推断认错 / 说不准）和「说不准的例如」，有对不上的条目再加进 `match-cases.mjs`。
- **论坛页面的真实 HTML 变体、TMDB 的真实返回只按现有代码的解析规则模拟过**，没有拿线上页面回放。
- Cloudflare Free 计划的 CPU 限制（每次调用 10ms 量级）测不出来。建判定表那一下的 CPU 和 v5.4 第一次查目录同一个量级。
  极限模式的扫描轮一次解析 12 页，比普通模式的 3 页多。真被平台掐了，降级机制会把下一轮的页数减半，跑完一整轮再恢复。
  代价是锁要等 40 秒才过期。
- **论坛能承受多快没法在本地测**：极限模式同时 4 条、间隔下限 120ms。被限速会自动翻倍、冷却。
  要是线上频繁看到「被论坛限速」，把 `TURBO` 设成 `0`，或者在页面上关掉开关。
- 测速用的是模拟延迟（论坛每页 450ms 上下），真实论坛的延迟和限速阈值会改变倍数。
- **实时清单的位置是按 Stream v25 的代码推的**：`file-list-v2.json`、`tv/list-v1.json`、`lib-ptr.json` 写在 Stream 的 `FILE_CACHE` 桶里。
  这个桶是不是挂在 `data.cuven.online`（旧总账所在的域名）上，我这边看不到部署配置。
  不是的话，片库面板会提示，配 `STREAM_KEY` 即可。
