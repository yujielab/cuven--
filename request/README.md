# Cuven 请求添加 Worker（tj.cuven.us）

App 里点「请求添加」，这个 Worker 就接管整条链：

1. 让影片库把片子推进 PikPak 的 `/auto`。
2. 盯着云下载到 100%。
3. 清洗下载的内容。
4. 让 VPS 上的 rclone 把它传到 Dropbox 的 `/auto`。
5. 文件抵达 Dropbox 的 `/auto` 就自动通过最终审核：App 上马上「立即播放」，不等工作人员挪到 ram / ram2（2.4，见下面「文件抵达 /auto 自动通过最终审核」）。

App 上显示成五步进度。代码见 [`worker.js`](worker.js)，测试见 [`tests/run.mjs`](tests/run.mjs)。

它连接另外两个 Worker：
- 影片库：[index/](../index/README.md)，lb.cuven.us，用 v7.0 的 `/api/link/versions` 和 `/api/pikpush`。
- 传输：transfer.cuven.us，用 909 版的 `/api/link/*`（907 / 908 也能跑，但没有逐个文件核对）。代码和说明见 [transfer/](../transfer/README.md)。

## 五个步骤

| App 上 | 内部阶段 | 做什么 | 出问题时 |
| --- | --- | --- | --- |
| ① 等待制片商 | `queued` | 问影片库这部片或这一季按规格排好的全部版本，取第一个没试过的，让影片库推进 PikPak 的 `/auto`（影片库用它自己配的 PikPak 账号建云下载任务）。 | 影片库这会儿推不了，就过几分钟再推；这个版本推不了，就换下一个。 |
| ② 等待回应 | `download` | 盯 PikPak 的云下载任务，进度直接显示在 App 上（只显示百分比）。 | 任务出错、2 小时没有进度、12 小时还没下完：删掉任务和文件，回到 ① 推下一个规格。 |
| ③ 等待品质管理 | `clean`（电影） | 文件夹里体积最大的视频（不算 sample / 预告）移到 `/auto`，原文件夹进回收站。下来的是单个视频就直接用。 | 没有视频：换规格。 |
| | `check`（剧集） | 传输 Worker 整理文件夹（删广告垃圾），再核对整季：总集数取标题里写的，标题没写就用 TMDB 上这一季已经播出的集数。 | 缺集、标题写着还在连载、没有认得出集号的视频：换规格（降档重试）。 |
| | `rename`（剧集） | 传输 Worker 按发行命名改文件夹名（默认 `rel` / 英文名 / `Cuven®`，面板里可改），等 rclone 的任务跑完。 | 失败重试 3 次，还不行就停下来等人。 |
| ④ 等待传输 | `copy` → `verify` → `purge` | rclone `webdav:auto/<名字>` → `dropbox:auto/<名字>`（先 copy）。传完等 45 秒，两端逐个文件核对路径和大小，一致了才删 PikPak 那份。 | 传输出错就重新 copy，最多 3 次。核对不一致见下面「两端核对」。 |
| | `purge` 之后（2.4） | 删完 PikPak 那份 = 文件抵达 `/auto`：**自动通过最终审核**，直接完成，不进第 5 步。同时请片库马上收录（Stream Worker 的 `/api/auto/sync`）。 | 片库还没收录、连不上：照样通过，之后每分钟催片库一次。片库是老版本：照样通过，日志写清楚要等工作人员挪进片库才能播放。 |
| ⑤ 最终发行审批 | `release` | 只有面板里关了「自动通过」才到这一步：每 5 分钟看一眼 `dropbox:auto/<名字>` 还在不在。 | — |
| 完成 | `done` | 文件抵达 `/auto` 自动通过（可以播放了），或者（关了自动通过时）工作人员把它挪去 ram / ram2、不在 `/auto` 里了（已发行）。 | — |

百分比 =（第几步 − 1 + 这一步的进度）÷ 5。例如刚进第 3 步是 40%，等发行是 80%，发行了是 100%。

其他规则：
- **跟上**：同一部片（剧集是同一季）已经有人在请求，后来的人就跟上那一条，不重复下载。
- **限额**：每个用户同时进行中最多 5 个，全部加起来最多 30 个（面板里可改）。等发行的不算。
- **失败后**：一天之内用户再点，拿回的还是那条失败的；面板里随时能重试。
- **出错退避**：同一步出错会按 2、4、8…30 分钟往后退（带 ±15% 抖动）。连续 20 次就停下来等人看。网络这类暂时的问题不算在这 20 次里，但一整天都连不上也会停下。

## 核心（2.0）：熔断、智能队列、资源位、看门狗

**熔断**：每个外部依赖单独记健康，面板的「系统」卡里看得到。四个依赖是影片库、传输（VPS）、PikPak、TMDB。
- **什么时候熔断**：同一个依赖连续 3 次暂时性失败就熔断。暂时性失败指连不上、超时、5xx、429、影片库忙。
- **熔断多久**：先熔断 2 分钟。到期放一次试探，通了就恢复；又失败就再熔断，时间翻倍：2 → 4 → 8 → 15 分钟封顶。
- **熔断期间**：要用它的请求原地等，不算出错次数，也不换规格。一部片不会因为 VPS 抖一下就被判失败。
- **不算依赖坏了的**：逻辑错误（4xx：参数不对、文件夹不在、作业没了）。

**智能队列**：每轮从到期的请求里按下面的顺序挑：
1. **先把开了头的做完**：发行检查 > 删 PikPak > 核对 > 传输 > 改名 / 清洗 > 云下载 > 排队中的。越往后的一步越早腾出位子，流水线不会堵在中间。
2. **公平**：排队中的按「这个人的第几个」打散，每个人的第一个先上。一个人连点五部，不会把别人挤到后面。
3. **人多优先**：同一档里，好几个人在等的那条优先，再按到期时间、先来后到。

面板里每条排队的请求都写着「排队第 N 位」。

**资源位**（面板「限额」里调）：
- PikPak 同时云下载默认 4 个。
- VPS 同时传输默认 2 个。rclone 一次跑太多传输会把内存吃满、整个进程被杀，这也是 52x 的来源之一。

满了就排队等，不算出错。

**批量**：一轮里要问的 rclone 作业一次问完（`/api/link/jobs`），等发行的列一次 `dropbox:auto` 一起看（`/api/link/exists {items}`）。快下完的云下载看得勤（1 分钟），刚开始的慢慢看（3 分钟）。

**看门狗**：
- 传输一小时没有新字节、改名半小时没有进展：先停掉作业再重开（rclone copy 会跳过已经传完的文件），最多 3 次。
- VPS 重启、rclone 作业丢了：从断点重开，最多 5 次。

**状态和写入**：
- 状态只许按流程走（代码里的 `FLOW`）。跳步是程序错误，会停下来等人，不会悄悄跳过一步。
- 每一步都可以重入：中途被掐（预算、超时、VPS 重启），下一轮从同一步接着做，不会重复推送、重复开传输。
- 一轮里的请求更新和日志攒起来，用一个事务写进 D1。面板刚改过的那条（`rev` 对不上）不覆盖，面板说了算。

**App 轮询**：`/app/requests` 带 ETag，没变化回 304。App 问失败了按 2 的倍数放慢（最慢 10 分钟），通了马上恢复。

**和传输 Worker 的配合**：要配 908 版，有 52x 自动重试和批量接口。老版本也能跑，只是退回一个一个问。

## 两端核对（2.1）

以前经常「两端核对不一致，重新传输」。原因有三：
- 任何一边列目录失败（WebDAV 列大目录慢、52x、VPS 正忙）都被当成不一致，于是整个重传。
- 源头用 WebDAV 列，PikPak 的 WebDAV 列表会缓存。
- 只比总数和总字节。

现在配合传输 Worker 909：

**怎么比：**
- 两端逐个文件比路径和大小。源头用 rclone 原生 pikpak 后端列（API 直接给大小，不缓存）。
- 路径按 Unicode NFC、不分大小写比（Dropbox 不分大小写）。
- 这些不算：
  - Dropbox 存不了的系统文件（desktop.ini、thumbs.db、.DS_Store…）
  - 没下完的临时文件（.part、.!qB、.aria2…）
  - Dropbox 那边多出来的文件

**比出问题时：**

| 情况 | 怎么做 |
| --- | --- |
| 列目录失败 | 算没核对成：过会儿再核对，不补传，也不算次数。 |
| 刚传完 | 先等 45 秒再核对。 |
| 第一次不一致 | 隔 2 分钟再核对一次，还不一致才补传。 |
| 补传 | 只传缺的和大小不对的（rclone copy 会跳过已经一样的）。第二次补传起改从 PikPak 原生接口拿、只按大小判断，WebDAV 列表里没有或拿不到的文件也能补上。 |
| 补传 3 次还对不上 | 停下等人处理。失败原因和日志写清楚缺了哪些文件、哪些大小不对。 |

## 文件抵达 /auto 自动通过最终审核（2.4）

用户要求：当文件抵达 auto 自动通过最终审核，使影片可以播放。以前传进 Dropbox 的 `/auto` 以后要等工作人员挪进 ram / ram2；
2.2 改成片库收录了才算（最多等 15 分钟）；现在两端核对一致、PikPak 那份删了，就当场通过：

1. App 上 100%，详情页的按钮变「立即播放」，发「已就绪」通知。日志写「文件已抵达 /auto，自动通过最终审核」。
2. 同时请片库马上收录：`POST <STREAM_BASE>/api/auto/sync?item=<名字>&code=<请求编号>[&tv=1]`（Stream Worker v25.1 起把 `/auto` 叠进片库）。
   电影的名字是 `/auto` 里的那个文件名，剧集是那个文件夹名；也按追踪码认（见下一节）。
3. 片库当场就收录了：完事。还没收录（Dropbox 的列表慢几秒、片库连不上）：照样通过，之后每分钟催一次（前 15 次，之后每 30 分钟，最多一天），收录了就停。
   催片库只改记录，不动更新时间。App 里按「立即播放」时还没找到这一部，也会请片库马上收录一次再找。
4. 片库是老版本（`/api/auto/sync` 回 404）、关了 `AUTO_FOLDER`、口令对不上（401 / 403）：照样通过，日志写清楚要等工作人员挪进片库才能播放。
5. 以前停在「最终发行审批」的（升级之前进来的、片库那时还是老版本的）下一轮直接通过。

其他：
- 一轮里好几条要问片库的，一次问完。片库连不上、熔断不算出错。
- 控制面板「限额」那张卡里可以关掉（「文件抵达 /auto 自动通过最终审核」），关了就照旧等工作人员发行。「测试连接」会写片库收不收录 `/auto`。
- 工作人员以后照旧把 `/auto` 里的挪进 ram / ram2：片库那边 `/auto` 那份消失、新位置加进来，App 照常能放（「继续观看」按追踪码跟过去）。

## 名字里带追踪码（2.3）

用户要求：在文件和文件夹名中带上 auto-TMDB唯一码-内部代码，就可以持续追踪。开始传 Dropbox 之前，在 PikPak 上把这一部改个名：

| | 原名 | 改成 |
| --- | --- | --- |
| 电影（文件） | `Fight.Club.1999.1080p.mkv` | `Fight.Club.1999.1080p.[auto-m550-r13].mkv` |
| 剧集（文件夹） | `Game.of.Thrones.S02.1080p.[Full-4]-Cuven®` | `Game.of.Thrones.S02.1080p.[Full-4]-Cuven®.[auto-tv1399s2-r14]` |

- `m` / `tv` + TMDB 编号：电影和剧集的编号会重复，所以带上类型；剧集再带季（`s2`）。
- `r` + 这条请求的编号（面板里的 `#13`）：带个 `r` 是免得 `2001` 这种编号被当成年份。
- 加在扩展名前面；名字是空格分隔的就用空格，点分隔的用点。之后的传输、核对、删 PikPak、发行检查都用新名字。
- 改不成（面板里关了、没填 PikPak、`/auto` 里找不到、PikPak 拒绝）就照原名传，日志写一句，不耽误。

有了它：
- **片库认得准**：Stream Worker v25.2 起直接按名字里的 TMDB 编号认片，不靠文件名猜；剧集的 TMDB 编号当场就有。
- **问收录时连追踪码一起问**（`/api/auto/sync?code=13`）：名字大小写对不上、已经被挪进 ram / ram2，都认得出来。
- **就绪以后接着追踪**：30 分钟一轮（一次问完，最多 40 条），最多追 30 天。工作人员挪去哪儿了，面板里那一条下面写「→ /ram/…」，日志写「工作人员已归档：…」。
  连着 6 次（3 小时）哪儿都找不到（改了名、删了）才停，面板写「找不到了」。追踪只改记录，不动更新时间（App 上「最近」的时间不跳）。
- **App 里「继续观看」和片单跟着走**：工作人员挪了位置，App 按追踪码把进度和片单接到新路径上，看到一半的接着放。

**工作人员挪的时候别改名**（至少留着 `[auto-…]` 那一截），不然就追不到了。

## App 接口

不需要口令。请求类的接口要带 `x-cuven-user`，值是 `encodeURIComponent(用户名)`。这个用户名要在 check.cuven.us 上查得到（`/check/<用户名>` 回 `exists: true`，和 App 登录时同一个接口），核对过的缓存 7 天。

| 接口 | 回包 |
| --- | --- |
| `GET /app/catalog?src=movie\|tv\|all&q=&page=&sort=new\|vote\|hot\|spec&own=all\|hide&min=` | 索引里的全部已知影片和剧集（`id` 是 TMDB 编号）。`src=all` 时电影、剧集交替排。每条带 `req`（这部片的请求进度）。 |
| `GET /app/detail?src=&id=&season=` | `known`（索引里有没有）、`count`（大于 0 才能请求）、`seasons`、`season`、`req`（这一部或这一季的进度）、`reqs`（每一季的进度）。 |
| `GET /app/requests` | 我的请求：进行中的，加上 30 天内结束的。 |
| `POST /app/requests { src, id, season }` | 请求添加。回 `created`（新建）、`joined`（跟上已有的）或 `failedRecently`（刚失败过）。 |

一条请求的进度（`req` / `request` / `items[]`）：

```json
{ "id": 12, "src": "tv", "tmdb": 1399, "season": 2, "title": "权力的游戏", "poster": "/x.jpg",
  "stage": "copy", "state": "active", "step": 4, "steps": 5, "pct": 69,
  "label": "等待传输", "created": 1763518000000, "updated": 1763520000000 }
```

`state` 是 `active` / `done` / `failed` / `cancelled`。失败和取消的 `step` 停在出事的那一步。

给 App 的进度**不带内部说明**：现在在做什么、出了什么错（`note`）、哪个版本（`spec`）、试过几个（`tries`）只有控制面板看得到。App 上那张卡只显示五步、百分比和一行固定的说明（「您可以返回，我们将在影片就绪时提醒您。添加流程一般不会超过一个小时。」）。

## 控制面板

打开 https://tj.cuven.us/ 输入 ADMIN_KEY，可以：

- **PikPak 账号**：填账号和密码，测试登录。测试时也会核对影片库给的 `/auto` 在这个账号里存在，也就是两边是同一个账号。
- **连接**：测试影片库、传输 Worker、片库（收不收录 `/auto`）能不能连上。
- **剧集命名**：改模板、语言、发行组。
- **限额**：改两个上限，也可以暂停定时任务、关掉「文件抵达 /auto 自动通过最终审核」和「名字里带追踪码」。
- **手动添加**：按 TMDB 编号直接添加一条请求。
- **请求列表**：现在推进、换规格、取消、重试、删除，以及看每一条的日志。

PikPak 密码用 ADMIN_KEY 派生的密钥（AES-GCM）加密后存进 D1。换了 ADMIN_KEY 要重新填一次密码。

## 部署

### Cloudflare 面板

1. **建 D1**：存储和数据库 → D1 → 创建，名字叫 `cuven-request`。表不用手动建，Worker 第一次运行时会自己建。
   表名都带 `tj_` 前缀（`tj_req` / `tj_kv` / `tj_log`），和别的 Worker 共用一个库也不会撞名（1.0 用的是 `req` / `kv` / `log`，库里原来就有一张 `kv` 时会报 `no such column: exp`，1.1 修了）。
2. **建 Worker**：Workers 和 Pages → 创建 → Hello World，名字叫 `cuven-request`。把 `worker.js` 的全部内容粘进去，然后部署。
3. **设置 → 绑定**：添加 D1 数据库，变量名填 `DB`，选第 1 步建的库。
4. **设置 → 变量和机密**，三个都选「密钥」：
   - `ADMIN_KEY`：自己定一个长口令，用来登录控制面板。
   - `LB_GATE`：和影片库 Worker 的 `GATE` 一样。
   - `LINK_KEY`：和传输 Worker 的 `LINK_KEY` 一样。
5. **设置 → 触发事件**：添加 Cron 触发器 `* * * * *`（每分钟一次）。
6. **设置 → 域和路由**：添加自定义域 `tj.cuven.us`。
7. 打开 https://tj.cuven.us/，填 PikPak 账号和密码。点「测试登录」和「测试影片库 / 传输」，都应该是绿的。

可选变量（下面是默认值，一般不用改）：
- `LB_BASE` = https://lb.cuven.us
- `TRANSFER_BASE` = https://transfer.cuven.us
- `STREAM_BASE` = https://stream.cuven.online（TMDB 分季集数，和 2.2 起的 `/api/auto/sync`）
- `STREAM_SYNC_KEY`（密钥，可选）：Stream Worker 配了 `AUTO_SYNC_KEY` 时填同一个
- `ACCOUNT_BASE` = https://check.cuven.us
- `AUTO_DIR` = auto

### wrangler

```sh
cd request
wrangler d1 create cuven-request          # 把打印出来的 database_id 填进 wrangler.toml
wrangler secret put ADMIN_KEY
wrangler secret put LB_GATE
wrangler secret put LINK_KEY
wrangler deploy
```

### 另外几个 Worker 要做的

- **片库**（Stream Worker，`Stream_v25.js` v25.2 起）：重新部署就有 `/auto` 那一层、`/api/auto/sync` 和追踪码，不用新变量（`AUTO_FOLDER` 默认 `/auto`）。不部署也没关系，这里照旧等工作人员发行。

- **影片库**：部署 v7.0 的 `index/worker.js`。`PIKPAK_USER` 必须和这里面板里填的是同一个 PikPak 账号。
- **传输**（909 版，[transfer/](../transfer/README.md)）：设置下面这些变量。908 起连 VPS 遇到 521 / 522 / 523 会自动重试（见上面「核心」），可选的 `VPS_ALT` 填同一台 VPS 的备用入口（不走 Cloudflare 代理的灰云子域名，或者 IP），重试时轮流走它。
  - `LINK_KEY`（密钥）：和这里的一样。
  - `VPS_PASS`（密钥）：rclone rcd 的密码。
  - 以下有默认值，一般不用改：
    - `VPS_HOST` = vps2.cuven.us
    - `VPS_PORT` = 8080
    - `VPS_USER` = admin
    - `RC_WEBDAV` = webdav:
    - `RC_PIKPAK` = pikpak:
    - `RC_DROPBOX` = dropbox:

- **VPS 上的 rclone**：要有三个 remote：
  - `webdav:`：PikPak 的 WebDAV，用来读。
  - `pikpak:`：原生 PikPak 后端，用来改名和删除。
  - `dropbox:`

## 免费计划的用量

- 每分钟跑一轮，一轮最多推进 24 条请求，子请求不超过 42 个（免费计划的上限是 50）。
- 云下载的进度一轮只问 PikPak 一次，所有条目共用。
- 传输 / 改名中的作业一轮一次问完（`/api/link/jobs`）。等发行的每 5 分钟一起看一次（`/api/link/exists`）。
- 熔断中的依赖一次都不碰。

测试不需要网络：

- 影片库、传输、PikPak、TMDB 分季、账户核对都在测试里模拟，时钟是假的，可以手动拨。
- 覆盖了电影全流程（推送、出错换规格、清洗、传输、核对、删除、等发行、已发行）。
- 覆盖了剧集全流程（缺集降档、按 TMDB 核对集数、改名、两端对不上重传）。
- 还覆盖了目录和详情带进度、限额、刚失败过、面板的取消和重试、没配 PikPak 时的等待。
- 2.0 的核心：
  - 资源位：每个人的第一个先上、排队位置；VPS 位子满了排队，调大了马上开。
  - 两个传输作业一轮只问一次。
  - 看门狗：传输一小时没进展先停掉再重开；作业丢了从断点重开。
  - 熔断：VPS 连着出错就熔断，熔断中一次都不碰，请求原地等不失败，到期试探通了恢复。
  - `/app/requests` 没变就回 304。
- 共用 D1：别人的同名表不碰，缺的列自己补。
- 两端核对（2.1）：
  - 列目录失败不补传；第一次不一致隔 2 分钟再核对一次，再核对就一致了的一次都不重传。
  - 补传：第一次从 WebDAV，第二次起从 PikPak 原生接口、只按大小；补传 3 次还对不上才停，PikPak 那份不删。
- 追踪码（2.3）：
  - 电影文件、剧集文件夹改名带上追踪码（扩展名前面、剧集带季），传输用新名字。
  - 按追踪码认出就绪（名字大小写对不上也行）；问到时已经被挪走也算就绪，归宿直接记下。
  - 就绪以后 30 分钟一轮追踪：找到被挪进 /ram 就记下来、不再追；只改记录不动更新时间；连着 6 次找不到才放弃。
  - PikPak 不让改名就照原名传；面板能关掉。
- 文件抵达 /auto 自动通过最终审核（2.4）：
  - 片库当场收录：通过、可以播放，不进最终发行审批、不等人挪。
  - 片库还没收录 / 连不上：照样通过，每分钟催片库，收录了就停；催片库不动 App 上的时间。
  - 老版本片库：照样通过，日志写清楚要等人挪进片库；不再催。
  - 停在最终发行审批的下一轮直接通过；好几条一次问完；面板能关掉；「测试连接」写清楚收不收录。

## 没有验证到的

- 没有连真的 PikPak 和 rclone 跑过。PikPak 云下载任务和文件的字段（`phase`、`progress`、`file_id`）按公开客户端的用法写的。`files:batchMove`、`files:batchTrash`、`DELETE /drive/v1/tasks` 也一样。
- 电影移到 `/auto` 时如果撞名，PikPak 怎么处理不确定。移完会重新读一次文件名，传输用读回来的名字。
