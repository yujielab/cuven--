# Cuven 请求添加 Worker（tj.cuven.us）

App 里点「请求添加」，这个 Worker 就接管整条链：

1. 让影片库把片子推进 PikPak 的 `/auto`（2.6 起剧集推进 `/auto/ram2`）。
2. 盯着云下载到 100%。
3. 清洗下载的内容。
4. 凑够 16 部清洗好的，让 VPS 上的 rclone 用一个作业一起传到 Dropbox 的 `/auto`（剧集传到 `/auto/ram2`），16 路并行传输、16 路并发核对（2.6，见下面「请求中心批量提交、凑批传输」）。
5. 文件抵达 Dropbox 的 `/auto` 就自动通过最终审核：App 上马上「立即播放」，不等工作人员挪到 ram / ram2（2.4，见下面「文件抵达 /auto 自动通过最终审核」）。

2.6 起 App 的请求中心先把要请求的放进请求篮（最多 50 部电影 / 剧集的一季，只存在手机上），按「确认」一次提交（`POST /app/requests/batch`）。
老版本 App 一部一部提交（`POST /app/requests`）照样能用，也一样凑批传。

App 上显示成五步进度。代码见 [`worker.js`](worker.js)，测试见 [`tests/run.mjs`](tests/run.mjs)。

它连接另外两个 Worker：
- 影片库：[index/](../index/README.md)，lb.cuven.us，用 v7.0 的 `/api/link/versions` 和 `/api/pikpush`。
- 传输：transfer.cuven.us，用 910 版的 `/api/link/*`（批量传输、剧集区 `sub`）。909 也能跑，只是一部一部传、剧集照旧放 `/auto`；907 / 908 还没有逐个文件核对。代码和说明见 [transfer/](../transfer/README.md)。

## 五个步骤

| App 上 | 内部阶段 | 做什么 | 出问题时 |
| --- | --- | --- | --- |
| ① 等待制片商 | `queued` | 问影片库这部片或这一季按规格排好的全部版本，取第一个没试过的，让影片库推进 PikPak 的 `/auto`（影片库用它自己配的 PikPak 账号建云下载任务）。2.6 起剧集推进 `/auto/ram2`。请求中心一次提交的，版本在这一步才问。 | 影片库这会儿推不了，就过几分钟再推；这个版本推不了，就换下一个；一个版本都没有：失败。 |
| ② 等待回应 | `download` | 盯 PikPak 的云下载任务，进度直接显示在 App 上（只显示百分比）。 | 任务出错、2 小时没有进度、12 小时还没下完：删掉任务和文件，回到 ① 推下一个规格。 |
| ③ 等待品质管理 | `clean`（电影） | 文件夹里体积最大的视频（不算 sample / 预告）移到 `/auto`，原文件夹进回收站。下来的是单个视频就直接用。 | 没有视频：换规格。 |
| | `check`（剧集） | 传输 Worker 整理文件夹（删广告垃圾），再核对整季：总集数取标题里写的，标题没写就用 TMDB 上这一季已经播出的集数。 | 缺集、标题写着还在连载、没有认得出集号的视频：换规格（降档重试）。 |
| | `rename`（剧集） | 传输 Worker 按发行命名改文件夹名（默认 `rel` / 英文名 / `Cuven®`，面板里可改），等 rclone 的任务跑完。 | 失败重试 3 次，还不行就停下来等人。 |
| ④ 等待传输 | `ready`（2.6） | 名字加上追踪码，然后停着等凑批：清洗好的凑够 16 部（面板里调），一起进一个 rclone 作业。关了批量传输、传输 Worker 是老版本：不停，直接 `copy`。 | 凑不满也不干等，见下面「请求中心批量提交、凑批传输」。 |
| | `copy` → `verify` → `purge` | rclone `webdav:auto/<名字>` → `dropbox:auto/<名字>`（先 copy；剧集是 `auto/ram2/<名字>`；2.6 起一批一个作业）。传完等 45 秒，两端逐个文件核对路径和大小，一致了才删 PikPak 那份。 | 传输出错就重新 copy，最多 3 次。核对不一致见下面「两端核对」；批量里对不上的，等这一批传完再一个一个补传。 |
| | `purge` 之后（2.4） | 删完 PikPak 那份 = 文件抵达 `/auto`：**自动通过最终审核**，直接完成，不进第 5 步。同时请片库马上收录（Stream Worker 的 `/api/auto/sync`）。 | 片库还没收录、连不上：照样通过，之后每分钟催片库一次。片库是老版本：照样通过，日志写清楚要等工作人员挪进片库才能播放。 |
| ⑤ 最终发行审批 | `release` | 只有面板里关了「自动通过」才到这一步：每 5 分钟看一眼 `dropbox:auto/<名字>` 还在不在。 | — |
| 完成 | `done` | 文件抵达 `/auto` 自动通过（可以播放了），或者（关了自动通过时）工作人员把它挪去 ram / ram2、不在 `/auto` 里了（已发行）。 | — |

百分比 =（第几步 − 1 + 这一步的进度）÷ 5。例如刚进第 3 步是 40%，等待凑批是 60%，等发行是 80%，发行了是 100%。

其他规则：
- **跟上**：同一部片（剧集是同一季）已经有人在请求，后来的人就跟上那一条，不重复下载。
- **限额**：每个用户同时进行中最多 50 个，全部加起来最多 200 个（面板里可改，最多 100 / 1000；2.5 是 5 / 30）。等发行的不算。请求中心一次最多提交 50 条。
- **失败后**：一天之内用户再点，拿回的还是那条失败的；面板里随时能重试。
- **出错退避**：同一步出错会按 2、4、8…30 分钟往后退（带 ±15% 抖动）。连续 20 次就停下来等人看。网络这类暂时的问题不算在这 20 次里，但一整天都连不上也会停下。

## 核心（2.0）：熔断、智能队列、资源位、看门狗

**熔断**：每个外部依赖单独记健康，面板的「系统」卡里看得到。四个依赖是影片库、传输（VPS）、PikPak、TMDB。
- **什么时候熔断**：同一个依赖连续 3 次暂时性失败就熔断。暂时性失败指连不上、超时、5xx、429、影片库忙。
- **熔断多久**：先熔断 2 分钟。到期放一次试探，通了就恢复；又失败就再熔断，时间翻倍：2 → 4 → 8 → 15 分钟封顶。
- **熔断期间**：要用它的请求原地等，不算出错次数，也不换规格。一部片不会因为 VPS 抖一下就被判失败。
- **不算依赖坏了的**：逻辑错误（4xx：参数不对、文件夹不在、作业没了）。

**智能队列**：每轮从到期的请求里按下面的顺序挑：
1. **先把开了头的做完**：发行检查 > 删 PikPak > 核对 > 传输 > 改名 / 清洗 > 云下载 > 排队中的。越往后的一步越早腾出位子，流水线不会堵在中间。
2. **公平**：排队中的按「这个人的第几个」打散，每个人的第一个先上。一个人连点五部，不会把别人挤到后面。
3. **人多优先**：同一档里，好几个人在等的那条优先，再按到期时间、先来后到。

面板里每条排队的请求都写着「排队第 N 位」。

**资源位**（面板「限额」里调）：
- PikPak 同时云下载默认 16 个（2.6，凑得满一批；2.5 是 4 个），最多 20 个。
- VPS 同时传输默认 2 个（单个传输）。rclone 一次跑太多传输会把内存吃满、整个进程被杀，这也是 52x 的来源之一。
  批量传输在跑的时候它一个作业就占着 VPS，单个传输一律排队等它传完。

满了就排队等，不算出错。

**批量**：一轮里要问的 rclone 作业一次问完（`/api/link/jobs`），等发行的列一次 `dropbox:auto` 一起看（`/api/link/exists {items}`）。快下完的云下载看得勤（1 分钟），刚开始的慢慢看（3 分钟）。

**看门狗**：
- 传输一小时没有新字节、改名半小时没有进展：先停掉作业再重开（rclone copy 会跳过已经传完的文件），最多 3 次。
- VPS 重启、rclone 作业丢了：从断点重开，最多 5 次。

**状态和写入**：
- 状态只许按流程走（代码里的 `FLOW`）。跳步是程序错误，会停下来等人，不会悄悄跳过一步。
- 每一步都可以重入：中途被掐（预算、超时、VPS 重启），下一轮从同一步接着做，不会重复推送、重复开传输。
- 一轮里的请求更新和日志攒起来，用一个事务写进 D1。面板刚改过的那条（`rev` 对不上）不覆盖，面板说了算。

**App 轮询**：`/app/requests` 带 ETag，没变化回 304。App 问失败了按 2 的倍数放慢（最慢 10 分钟），通了马上恢复。

**和传输 Worker 的配合**：要配 908 版以上，有 52x 自动重试和批量接口（2.6 的凑批传输要 910）。老版本也能跑，只是退回一个一个问。

## 请求中心批量提交、凑批传输（2.6）

用户要求：请求添加先放进请求中心（最多 50 部电影 / 剧集的一季），按「确认」一次提交；服务器让每一部走完 PikPak 云下载和清洗
（电影路径还是 `/auto`，剧集改成 `/auto/ram2`），至少 16 部下完、清洗好了再一起传，16 路并行传输、16 路并发核对，效率最高；
批量传输时 App 上有动画和进度条。

**一次提交**（`POST /app/requests/batch`）：
- 一组 SQL 做完（`json_each` 一个参数，D1 一条语句最多绑 100 个参数），不一条一条问影片库：新建的先用 App 给的片名、年份、海报占位，
  版本在 ① 那一步才问（没有资源的在那一步失败）。50 条也只用一两个子请求（核对用户名，缓存 7 天）。
- 每条回一个结果：`created`（新建）、`joined`（已经有人在请求，跟上）、`failedRecently`（一天之内失败过，拿回那条）、
  `limit`（超了每个人的 / 全部的限额，带 `cap: user | global`）、`invalid`（`src` / `id` / 季认不得）。篮子里重复的按第一次出现的那条算。
- 新建用 `INSERT OR IGNORE` 再查一遍：两个人同时提交同一部，唯一索引挡住后来的那条，后来的算跟上（不会整批回滚）。
- 同一次提交的记同一个 `bid`（提交组）。老版本 App 一部一部提交的 `bid = 0`。

**等待凑批**（新的一步 `ready`，App 上还是 STEP 4「等待传输」，60%）：
- 清洗 / 改名好了先在这一步加追踪码（同一个文件夹一轮只列一次：16 部一起加也只列一次 `/auto`），然后停着，10 分钟才自己醒一次，
  不占每轮 24 条的名额；凑批那一步一轮一次把它们一起挑走。
- 凑够 `batchMin`（默认 16）部就开一批，一批最多 `batchMax`（默认 16）部，先来的、人多的先进。多的凑下一批。**一次只跑一批。**
- 凑不满也不干等，下面任何一条成立就有几部传几部：
  - 最早的一部等了 `batchWait`（默认 30 分钟；老版本 App 一部一部提交的最多 10 分钟）；
  - 前面没有还会清洗好的了（推送 / 下载 / 清洗 / 核对整季 / 改名中的都没有，或者都在长时间退避）；
  - 等着的这几次提交（`bid`），每一部都清洗好了或者已经结束了。
- 不开批：VPS 熔断中；有一批在传；单个传输还在跑或者在排队（批量里对不上的补传先传完）。
- 「一次只跑一批」是这样保证的：
  - 每轮开头单独查在 `copy` 的批次（`tj_batch` 里 `stage = 'copy'`、没收尾的），和收尾中的（`verify` / `purge`）分开查。
    收尾中的批次可能停好几个小时（成员删 PikPak 一直出错、在退避），再多也挤不掉正在传的那一批；收尾中的每一批每轮都看一遍，一批不漏。
  - 开批的那一条 `INSERT` 带 `WHERE NOT EXISTS (在 copy 的批次)`：面板「推进一轮」不拿租约，和定时任务撞上时两边都走到开批，
    插不进去的那一边这一轮不开，也当那一批在传（单个传输接着排队）。
  - 库里万一已经有两批在 `copy`（升级之前撞出来的）：编号小的那批是正在传的，后面那批的成员一直停着（醒过来也不去核对）；
    前面那批传完，下一轮才开后面那批的作业，这期间不凑新的一批、不开单个传输。`/app/flow` 和面板给的也是编号小的那批。

**一批一个作业**（传输 Worker 910 的 `/api/link/batch-copy`）：
- `{ key: 批次编号, items: [{ item, kind, sub }], transfers: 16, checkers: 16 }`：一个 rclone `sync/copy`，过滤规则只圈出这一批；
  Dropbox 用 `chunk_size=16Mi,batch_mode=sync`、`BufferSize 8Mi`（16 路一起传，内存还在 VPS 撑得住的范围）。
- `key` 让它可以重来：开作业时这边超时了、VPS 抖了，下一轮同一个 key 再开，传输 Worker 认出正在跑的那个（`reused`），不会开出两个。
- 每轮只问一次作业进度（`/api/link/job { detail: 1 }`），成员的百分比按「传了多少字节 ÷ 开批时试列出来的总字节」一条 SQL 一起改。
  成员停在 `copy`，不带自己的作业号，15 分钟才醒一次。
- 看门狗在批次上：一小时没有新字节停掉重开，作业丢了（VPS 重启）从断点重开（rclone 跳过已经传完的）。
- 传完（成功、出错都一样）：成员一起去核对。一批一次 `batch-verify`（两边各列一次），每一部照旧按「两端核对」一条一条判断；
  一致的 8 个一次 `batch-purge` 删 PikPak 那份（一轮最多两次），删掉的云下载任务一次删完，问片库收录也一次问完。
- 对不上的离开那一批，走原来一个一个补传的路；批量作业在跑的时候不开单个传输，等这一批传完再补。
- 批量里取消一部：这一批照常跑完（不停作业）；传完这一部不核对、不删，日志写清楚它传到 Dropbox 的那份留在原处。
- 退回一个一个传：传输 Worker 是老版本（909，`ping` 里没有 `caps: ['batch']`）；试列时发现这台 rclone 不认过滤规则（409 `nofilter`，
  6 小时内都一个一个传，不算 VPS 坏了）；批量作业一天都开不成。

**剧集放进 `/auto/ram2`**（面板里的「剧集放在 /auto 下面哪个文件夹」，默认 `ram2`，PikPak 和 Dropbox 一样）：
- PikPak 上的 `/auto/ram2` 问影片库要（`/api/pikpak?do=ls&parent=<auto>`，没有就 `do=mkdir`），文件夹编号存 tj_kv（`tv:id`）。
- 推送、按名字找下下来的文件夹、加追踪码都在那个文件夹里；给传输 Worker 的每个调用都带 `sub: 'ram2'`（整理、核对整季、改名、
  批量 / 单个传输、核对、删除、发行检查）；发行检查一次问完时剧集的名字放在 `tv` 里。
- 要和传输 Worker 的 `AUTO_TV_DIR`、Stream Worker 的 `AUTO_TV_SUB` 一样。对不上、传输 Worker 是 909（`ping` 里没有 `sub`）：剧集照旧放 `/auto`，
  面板的「系统」卡里写着。升级之前已经推进 `/auto` 的照旧在 `/auto` 走完。

**传输 Worker 会什么**：`ping` 回的 `caps` 存在 tj_kv（`tf:caps`），30 分钟问一次；面板「测试连接」也顺手记下。还没问到过的时候，清洗好的先在 `ready` 等着。

## 两端核对（2.1）

以前经常「两端核对不一致，重新传输」。原因有三：
- 任何一边列目录失败（WebDAV 列大目录慢、52x、VPS 正忙）都被当成不一致，于是整个重传。
- 源头用 WebDAV 列，PikPak 的 WebDAV 列表会缓存。
- 只比总数和总字节。

现在配合传输 Worker 909：

**怎么比：**
- 两端逐个文件比路径和大小。源头用 rclone 原生 pikpak 后端列（API 直接给大小，不缓存）。
- 路径按 Unicode NFC、不分大小写比（Dropbox 不分大小写）。
- 这些不算：
  - Dropbox 存不了的系统文件（desktop.ini、thumbs.db、.DS_Store…）
  - 没下完的临时文件（.part、.!qB、.aria2…）
  - Dropbox 那边多出来的文件

**比出问题时：**

| 情况 | 怎么做 |
| --- | --- |
| 列目录失败 | 算没核对成：过会儿再核对，不补传，也不算次数。 |
| 刚传完 | 先等 45 秒再核对。 |
| 第一次不一致 | 隔 2 分钟再核对一次，还不一致才补传。 |
| 补传 | 只传缺的和大小不对的（rclone copy 会跳过已经一样的）。第二次补传起改从 PikPak 原生接口拿、只按大小判断，WebDAV 列表里没有或拿不到的文件也能补上。 |
| 补传 3 次还对不上 | 停下等人处理。失败原因和日志写清楚缺了哪些文件、哪些大小不对。 |

## 文件抵达 /auto 自动通过最终审核（2.4）

用户要求：当文件抵达 auto 自动通过最终审核，使影片可以播放。以前传进 Dropbox 的 `/auto` 以后要等工作人员挪进 ram / ram2；
2.2 改成片库收录了才算（最多等 15 分钟）；现在两端核对一致、PikPak 那份删了，就当场通过：

1. App 上 100%，详情页的按钮变「立即播放」，发「已就绪」通知。日志写「文件已抵达 /auto，自动通过最终审核」。
2. 同时请片库马上收录：`POST <STREAM_BASE>/api/auto/sync?item=<名字>&code=<请求编号>[&tv=1]`（Stream Worker v25.1 起把 `/auto` 叠进片库）。
   电影的名字是 `/auto` 里的那个文件名，剧集是那个文件夹名；也按追踪码认（见下一节）。
3. 片库当场就收录了：完事。还没收录（Dropbox 的列表慢几秒、片库连不上）：照样通过，之后每分钟催一次（前 15 次，之后每 30 分钟，最多一天），收录了就停。
   催片库只改记录，不动更新时间。App 里按「立即播放」时还没找到这一部，也会请片库马上收录一次再找。
4. 片库是老版本（`/api/auto/sync` 回 404）、关了 `AUTO_FOLDER`、口令对不上（401 / 403）：照样通过，日志写清楚要等工作人员挪进片库才能播放。
5. 以前停在「最终发行审批」的（升级之前进来的、片库那时还是老版本的）下一轮直接通过。

其他：
- 一轮里好几条要问片库的，一次问完。片库连不上、熔断不算出错。
- 控制面板「限额」那张卡里可以关掉（「文件抵达 /auto 自动通过最终审核」），关了就照旧等工作人员发行。「测试连接」会写片库收不收录 `/auto`。
- 工作人员以后照旧把 `/auto` 里的挪进 ram / ram2：片库那边 `/auto` 那份消失、新位置加进来，App 照常能放（「继续观看」按追踪码跟过去）。

## 追踪码优先（2.5）

用户要求：优先识别 auto 的唯一 TMDB 码，快速核对、正确添加影片和剧集。

- **新请求先核对片库**：推送下载之前问片库一句（`/api/auto/sync?tmdb=m550`，剧集 `tv1399s2`）。片库里已经有带这个 TMDB 编号（剧集再加季）
  追踪码的那一部（以前的请求加的，在 `/auto` 或已经挪进 ram / ram2），就不再下载，直接就绪「片库里已有」，日志写是哪一条请求加的、在哪儿。
  零 PikPak、零 VPS。问不成（片库连不上、老版本）就照常下。
- 片库（Stream v25.3）判断 `/auto` 里是电影还是剧集也先看追踪码：`[auto-m…]` 一定是电影，`[auto-tv…]` 一定是剧集的一季；在线字幕也按追踪码的编号找。
- 索引库（v7.1）的「库中已有」也先看追踪码，按编号判。
- App 里「立即播放」先按追踪码找片库里的那一部（不用等片名认出来）。

## 名字里带追踪码（2.3）

用户要求：在文件和文件夹名中带上 auto-TMDB唯一码-内部代码，就可以持续追踪。开始传 Dropbox 之前，在 PikPak 上把这一部改个名：

| | 原名 | 改成 |
| --- | --- | --- |
| 电影（文件） | `Fight.Club.1999.1080p.mkv` | `Fight.Club.1999.1080p.[auto-m550-r13].mkv` |
| 剧集（文件夹） | `Game.of.Thrones.S02.1080p.[Full-4]-Cuven®` | `Game.of.Thrones.S02.1080p.[Full-4]-Cuven®.[auto-tv1399s2-r14]` |

- `m` / `tv` + TMDB 编号：电影和剧集的编号会重复，所以带上类型；剧集再带季（`s2`）。
- `r` + 这条请求的编号（面板里的 `#13`）：带个 `r` 是免得 `2001` 这种编号被当成年份。
- 加在扩展名前面；名字是空格分隔的就用空格，点分隔的用点。之后的传输、核对、删 PikPak、发行检查都用新名字。
- 改不成（面板里关了、没填 PikPak、`/auto` 里找不到、PikPak 拒绝）就照原名传，日志写一句，不耽误。

有了它：
- **片库认得准**：Stream Worker v25.2 起直接按名字里的 TMDB 编号认片，不靠文件名猜；剧集的 TMDB 编号当场就有。
- **问收录时连追踪码一起问**（`/api/auto/sync?code=13`）：名字大小写对不上、已经被挪进 ram / ram2，都认得出来。
- **就绪以后接着追踪**：30 分钟一轮（一次问完，最多 40 条），最多追 30 天。工作人员挪去哪儿了，面板里那一条下面写「→ /ram/…」，日志写「工作人员已归档：…」。
  连着 6 次（3 小时）哪儿都找不到（改了名、删了）才停，面板写「找不到了」。追踪只改记录，不动更新时间（App 上「最近」的时间不跳）。
- **App 里「继续观看」和片单跟着走**：工作人员挪了位置，App 按追踪码把进度和片单接到新路径上，看到一半的接着放。

**工作人员挪的时候别改名**（至少留着 `[auto-…]` 那一截），不然就追不到了。

## App 接口

不需要口令。请求类的接口要带 `x-cuven-user`，值是 `encodeURIComponent(用户名)`。这个用户名要在 check.cuven.us 上查得到（`/check/<用户名>` 回 `exists: true`，和 App 登录时同一个接口），核对过的缓存 7 天。

| 接口 | 回包 |
| --- | --- |
| `GET /app/catalog?src=movie\|tv\|all&q=&page=&sort=new\|vote\|hot\|spec&own=all\|hide&min=&year=` | 索引里的全部已知影片和剧集（`id` 是 TMDB 编号）。`src=all` 时电影、剧集交替排。每条带 `req`（这部片的请求进度）。`year`（2.6）：只要这一年的（App「全部影片」可申请那一边按年份分节）。 |
| `GET /app/detail?src=&id=&season=` | `known`（索引里有没有）、`count`（大于 0 才能请求）、`seasons`、`season`、`req`（这一部或这一季的进度）、`reqs`（每一季的进度）。 |
| `GET /app/requests` | 我的请求：进行中的，加上 30 天内结束的。 |
| `POST /app/requests { src, id, season }` | 请求添加（老版本 App）。回 `created`（新建）、`joined`（跟上已有的）或 `failedRecently`（刚失败过）。 |
| `POST /app/requests/batch { items: [{ src, id, season, title?, year?, poster? }] }` | （2.6）请求中心按「确认」一次提交，最多 50 条。回 `{ bid, items: [{ src, id, season, result, cap?, request? }] }`，`result` 见上面「请求中心批量提交、凑批传输」。超过 50 条、空的：400。 |
| `GET /app/flow` | （2.6）请求中心最上面那张卡：凑批进度和正在传的那一批。带 ETag，没变回 304。 |

一条请求的进度（`req` / `request` / `items[]`）：

```json
{ "id": 12, "src": "tv", "tmdb": 1399, "season": 2, "title": "权力的游戏", "poster": "/x.jpg",
  "stage": "copy", "state": "active", "step": 4, "steps": 5, "pct": 69,
  "label": "等待传输", "created": 1763518000000, "updated": 1763520000000 }
```

`state` 是 `active` / `done` / `failed` / `cancelled`。失败和取消的 `step` 停在出事的那一步。

2.6 起可能多三个字段（老版本 App 不认也没关系）：`bid`（请求中心哪一次提交的）、`batch`（正在哪一批批量传输里，`copy` / `verify` / `purge` 时）、
`wait: { ready, need }`（等待凑批的：等着几部、要几部）。`stage` 多了一个 `ready`。

`/app/flow`：

```json
{ "at": 1763520000000,
  "gate": { "ready": 5, "need": 16, "mine": 2, "oldest": 1763518000000, "launchBy": 1763519800000 },
  "batch": { "id": 7, "stage": "copy", "items": 16, "mine": [12, 15], "bytes": 8000000000, "total": 16000000000,
             "speed": 52428800, "eta": 160, "files": { "done": 5, "total": 26 }, "started": 1763519000000, "pct": 50 },
  "poll": 5 }
```

- `gate`：所有人等着凑批的有几部（`mine` = 其中我的），最早的什么时候进来，凑不满时最晚什么时候开（`launchBy`）。
- `batch`：没有在跑的批是 `null`。`stage` 是 `copy`（传输中）/ `verify`（核对）/ `purge`（删 PikPak、收尾）；`mine` 是这一批里我的请求编号。
  只有汇总的数，不带别人的片名和请求。
- 传输中的实时进度：问一次传输 Worker 的作业（缓存 5 秒，好几个人同时看也只问一次；VPS 熔断中不问，用定时任务每分钟记下的）。
- `poll`：App 多久再问（这一批在传 5 秒，平时 20 秒）。ETag 不算 `at`。

给 App 的进度**不带内部说明**：现在在做什么、出了什么错（`note`）、哪个版本（`spec`）、试过几个（`tries`）只有控制面板看得到。App 上那张卡只显示五步、百分比和一行固定的说明（「您可以返回，我们将在影片就绪时提醒您。添加流程一般不会超过一个小时。」）。

## 控制面板

打开 https://tj.cuven.us/ 输入 ADMIN_KEY，可以：

- **PikPak 账号**：填账号和密码，测试登录。测试时也会核对影片库给的 `/auto` 在这个账号里存在，也就是两边是同一个账号。
- **连接**：测试影片库、传输 Worker、片库（收不收录 `/auto`）能不能连上。
- **剧集命名**：改模板、语言、发行组。
- **限额**：改两个上限、两个资源位，也可以暂停定时任务、关掉「文件抵达 /auto 自动通过最终审核」和「名字里带追踪码」。
  2.6 起还有：批量传输开 / 关、凑够几部开一批（`batchMin`，默认 16）、一批最多几部（`batchMax`，最多 16）、最多等几分钟（`batchWait`，默认 30）、
  并行传输（`xfers`，Transfers，最多 16）、并发核对（`checkers`，最多 16）、请求中心一次最多提交几条（`basketMax`，最多 50）、
  剧集放在 `/auto` 下面哪个文件夹（`tvSub`，默认 `ram2`，空 = 直接放 `/auto`）。
- **系统**：各依赖的熔断、资源位、上一轮推进了几条、用了几个子请求（2.6 起还写着有几个被预算挡回去）；2.6 起还有凑批进度（等着几部 / 要几部、最晚什么时候开）、
  最近一批（传输中的字节、速度、还要多久，为什么开、出了什么错）、传输 Worker 会不会批量、剧集放在哪儿。
- **手动添加**：按 TMDB 编号直接添加一条请求。
- **请求列表**：现在推进、换规格、取消、重试、删除，以及看每一条的日志。2.6 起写着在哪一批、请求中心第几次提交、剧集在哪个区。
  - 等待凑批的也能换规格、取消（PikPak 那份一起删；取消后重试从推送那一步重来）。
  - 批量里的取消：见上面；批量里的重试：离开那一批，还没传完的回去等凑批。

PikPak 密码用 ADMIN_KEY 派生的密钥（AES-GCM）加密后存进 D1。换了 ADMIN_KEY 要重新填一次密码。

## 部署

### Cloudflare 面板

1. **建 D1**：存储和数据库 → D1 → 创建，名字叫 `cuven-request`。表不用手动建，Worker 第一次运行时会自己建。
   表名都带 `tj_` 前缀（`tj_req` / `tj_kv` / `tj_log`），和别的 Worker 共用一个库也不会撞名（1.0 用的是 `req` / `kv` / `log`，库里原来就有一张 `kv` 时会报 `no such column: exp`，1.1 修了）。
2. **建 Worker**：Workers 和 Pages → 创建 → Hello World，名字叫 `cuven-request`。把 `worker.js` 的全部内容粘进去，然后部署。
3. **设置 → 绑定**：添加 D1 数据库，变量名填 `DB`，选第 1 步建的库。
4. **设置 → 变量和机密**，三个都选「密钥」：
   - `ADMIN_KEY`：自己定一个长口令，用来登录控制面板。
   - `LB_GATE`：和影片库 Worker 的 `GATE` 一样。
   - `LINK_KEY`：和传输 Worker 的 `LINK_KEY` 一样。
5. **设置 → 触发事件**：添加 Cron 触发器 `* * * * *`（每分钟一次）。
6. **设置 → 域和路由**：添加自定义域 `tj.cuven.us`。
7. 打开 https://tj.cuven.us/，填 PikPak 账号和密码。点「测试登录」和「测试影片库 / 传输」，都应该是绿的。

可选变量（下面是默认值，一般不用改）：
- `LB_BASE` = https://lb.cuven.us
- `TRANSFER_BASE` = https://transfer.cuven.us
- `STREAM_BASE` = https://stream.cuven.online（TMDB 分季集数，和 2.2 起的 `/api/auto/sync`）
- `STREAM_SYNC_KEY`（密钥，可选）：Stream Worker 配了 `AUTO_SYNC_KEY` 时填同一个
- `ACCOUNT_BASE` = https://check.cuven.us
- `AUTO_DIR` = auto

## 免费计划的用量

- 每分钟跑一轮，一轮最多推进 24 条请求，子请求不超过 42 个（免费计划的上限是 50）。
- 云下载的进度一轮只问 PikPak 一次，所有条目共用。
- 传输 / 改名中的作业一轮一次问完（`/api/link/jobs`）。等发行的每 5 分钟一起看一次（`/api/link/exists`）。
- 熔断中的依赖一次都不碰。
- 上一轮用了几个子请求、有几个被预算挡回去（`over`，2.6）记在 tj_kv 的 `tick:last`，面板「系统」卡里写着。
  `fetches` 到不了 42 以上（第 43 个直接被挡回去，那一步下一轮再做），所以要看 `over`：凑批之前十几部一起清洗时偶尔会有，开批、核对、删除那几轮应该是 0。
- 批量传输（2.6）：开一批 1 个子请求；在传的时候一轮问 1 次作业进度（成员不用每轮排上）；一批核对 1 次；删 PikPak 8 个 1 次（一轮最多 2 次）
  加 1 次删云下载任务；问片库收录、新请求核对片库都一次问完。加追踪码一部 2 个（改名 + 读回来），同一个文件夹一轮只列一次。
- 请求中心一次提交 50 条：1 个子请求（核对用户名，7 天缓存），不问影片库。`/app/flow` 最多 1 个（实时进度，5 秒缓存）。
- D1 读的行数（免费计划一天 500 万行）：`tj_req` 不删旧的（就绪、失败的留着追踪、看历史），所以凑批、`/app/flow` 按 `stage` 查的
  都走 `tj_req_stage(stage, since)` 索引（2.6，`db()` 给老库也补上），只读等着凑批 / 还在路上的那几行，不再每轮把整张表读两遍。
  一个加好追踪码、等着凑批的都没有时，一轮末尾不再查第二遍。

## 测试

```sh
node request/tests/run.mjs
```

测试不需要网络：
- D1 用 node:sqlite 的内存库代替。
- 影片库、传输、PikPak、TMDB 分季、账户核对都在测试里模拟，时钟是假的，可以手动拨。
- 覆盖了电影全流程（推送、出错换规格、清洗、传输、核对、删除、等发行、已发行）。
- 覆盖了剧集全流程（缺集降档、按 TMDB 核对集数、改名、两端对不上重传）。
- 还覆盖了目录和详情带进度、限额、刚失败过、面板的取消和重试、没配 PikPak 时的等待。
- 2.0 的核心：
  - 资源位：每个人的第一个先上、排队位置；VPS 位子满了排队，调大了马上开。
  - 两个传输作业一轮只问一次。
  - 看门狗：传输一小时没进展先停掉再重开；作业丢了从断点重开。
  - 熔断：VPS 连着出错就熔断，熔断中一次都不碰，请求原地等不失败，到期试探通了恢复。
  - `/app/requests` 没变就回 304。
- 共用 D1：别人的同名表不碰，缺的列自己补。
- 两端核对（2.1）：
  - 列目录失败不补传；第一次不一致隔 2 分钟再核对一次，再核对就一致了的一次都不重传。
  - 补传：第一次从 WebDAV，第二次起从 PikPak 原生接口、只按大小；补传 3 次还对不上才停，PikPak 那份不删。
- 追踪码优先（2.5）：片库里已有带这个 TMDB 编号追踪码的那一部 → 不推送、直接就绪，记下在哪儿；片库连不上照常下。
- 追踪码（2.3）：
  - 电影文件、剧集文件夹改名带上追踪码（扩展名前面、剧集带季），传输用新名字。
  - 按追踪码认出就绪（名字大小写对不上也行）；问到时已经被挪走也算就绪，归宿直接记下。
  - 就绪以后 30 分钟一轮追踪：找到被挪进 /ram 就记下来、不再追；只改记录不动更新时间；连着 6 次找不到才放弃。
  - PikPak 不让改名就照原名传；面板能关掉。
- 请求中心批量提交、凑批传输（2.6）：
  - `/app/requests/batch`：`created` / `joined` / `failedRecently` / `limit`（每个人的、全部的）/ `invalid`，不问影片库，一个 bid；重复提交不重复加人；超过 50 条 400。
  - 端到端：14 部电影 + 4 季剧集一次提交 → 下载 / 清洗（剧集在 `/auto/ram2`，PikPak 的文件夹问影片库建一次）→ 等待凑批时停着 →
    凑满 16 部一个 `batch-copy`（Transfers 16 / Checkers 16，key = 批次编号，名字都带追踪码）→ 成员进度一条 SQL 一起改 →
    一次 `batch-verify`、8 个一次 `batch-purge` → 就绪；对不上的那一季等下一批传完才单个补传；批量里取消的不核对不删。
  - 剧集的每一个传输调用都带 `sub: ram2`；每一轮的子请求都没超 42；开批、核对、删除那几轮没有子请求被预算挡回去（`over = 0`），
    分别只有一个 `batch-copy`、一个 `batch-verify`、两个 `batch-purge`；从开批到全部就绪每一轮 `over` 都是 0。
